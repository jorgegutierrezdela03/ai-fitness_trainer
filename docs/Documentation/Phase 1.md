# Phase 1: Definition, Initial Baseline and Evaluation

**Objective:** To develop a reproducible core system that generates personalized training plans based on user profiles and requests, without relying on external knowledge, and to establish an evaluation protocol for the generated results.

## P1-01 — Define Project Scope and Requirements

Define the scope, target users, functional requirements, and constraints of the AI Fitness Trainer baseline.

### P1-01.1 — Define Target Population and Project Scope

#### Objective
Define the target users, training objectives, and initial boundaries of the AI Personal Trainer.

#### Target Population
Adults aged 18 or older who perform or intend to perform exercise in a conventional gym, with different experience levels and general fitness goals.

#### Inclusion Criteria
- Generally healthy individuals without conditions requiring clinical exercise prescription.
- Beginners, intermediate, and advanced recreational gym users.
- Users seeking personalized training for general fitness, strength, hypertrophy, muscular endurance, cardiovascular health, or body composition.

#### Exclusion Criteria
- Elite athletes requiring specialized training.
- Marathon, triathlon, or competitive endurance preparation.
- Competitive bodybuilding and specialized calisthenics.
- Clinical rehabilitation or medically supervised exercise.
- Nutritional planning and dietary interventions.

#### Training Context
The system will support conventional gym-based training using machines, dumbbells, barbells, free weights, cables, and cardiovascular equipment.

#### Supported Training Objectives
- Strength.
- Hypertrophy.
- Muscular endurance.
- General fitness.
- Fat loss through exercise.
- Cardiovascular fitness.
- Combined resistance and cardiovascular training.

### P1-01.2 — Define User Profile Specifications

#### Objective
Define the user information required to generate personalized training plans.

#### User Profile

##### Basic Information
- Age: Required.
- Sex: Optional.
- Height: Optional.
- Weight: Optional.

Height and weight will remain optional until their usefulness for different training objectives is evaluated.

##### Training Experience
Required. Three predefined levels:
- Beginner.
- Intermediate.
- Advanced.

##### Training Goals
Required. Select up to two primary objectives:
- Strength.
- Hypertrophy.
- Fat loss.
- Cardiovascular fitness.
- Muscular endurance.
- General fitness.

##### Training Availability
- Available training days per week: Required.
- Available session duration: Required.

##### Training Preferences and Restrictions
Optional questions covering:
- Exercises the user prefers to avoid.
- Equipment or gym limitations.
- Preferred training style.

The system will assume a conventional gym environment while allowing users to specify preferences or limitations related to their training environment.

##### Physical Limitations
Required Yes/No question:

**Do you have any physical limitations that may affect your training?**

If Yes:
- Select affected body areas (shoulder, elbow, wrist, back, hip, knee, ankle, or other).
- Provide an optional free-text description.

The system will use this information to identify and respect training restrictions without providing clinical or medical exercise prescription.

#### Data Considerations
- Prioritize structured inputs and predefined options.
- Use optional fields when information is not essential for initial plan generation.
- Minimize the collection of personal and health-related information.
- Initially use synthetic user profiles for experimental evaluation.


### P1-01.3 — Define User Profile Data Model and Validation

#### Objective
Implement and validate the data structures required for user profiles and session generation requests according to the functional specifications.

#### Implementation Summary
- **Tooling:** Implemented in `src/schemas/user_profile.py` using **Pydantic (v2)** to provide strict type safety, automatic runtime parsing, and deterministic contract enforcement for inputs consumed by the system and LLM prompts.
- **Data Models:**
  - `PhysicalLimitations`: Handles health limitations via a conditional validator ensuring that `affected_areas` is populated if and only if limitations are declared.
  - `UserProfile`: Encapsulates user demographic metadata, experience level, prioritized goals, availability boundaries, and environmental restrictions.
  - `SessionGenerationInput`: Unifies the structured `UserProfile` with the free-text `session_request` into a single validated input payload.
- **Verification:** Schema functionality and boundary rejection (negative testing) are demonstrated programmatically in `notebooks/schema_validation_demo.ipynb` using reference test cases from `data/evaluation/examples/sample_user_input.json`.

## P1-02 — Define Output Format

Define a standardized output structure for the training plans generated by the LLM.


### P1-02.1 — Define Training Plan Output Structure

#### Objective
Define a standardized structure for the training plans generated by the LLM, specifying the information required to represent training sessions, exercises, and their associated instructions.

#### 1. Session Header

Each training session will contain:

- Descriptive title.
- Main session focus.
- Estimated total duration in minutes.

The following metadata will also be included in the final output:

- Session ID.
- User ID.
- Generation date and time.

**Metadata considerations:**

Session ID, User ID, and generation timestamp must be generated and managed by the Python backend, not by the LLM. The backend will add this information to the generated plan.

These fields will support storage, identification, and future session history analysis. They will not be part of the initial training plan evaluation.

#### 2. Warm-up

Optional section that may include:

- **General activation:** Joint mobility exercises or light cardiovascular activity.
- **Specific warm-up:** Activities related to the main exercises.
- **Warm-up sets:** Additional preparation sets for the first main exercises, when appropriate.

The inclusion and content of the warm-up will depend on the session and its exercises.

#### 3. Main Training Block

A structured and ordered list of exercises included in the session.

Each exercise will contain the following information:

**General Information**
- Exercise name.
- Exercise modality:
  - Strength.
  - Cardio.
  - Mobility.
- Exercise priority within the session:
  - Primary.
  - Secondary.
  - Accessory.
- Primary muscle group, when applicable.
- Secondary muscle groups, when applicable.

The priority classification will help represent the importance of each exercise in relation to the session focus and facilitate the evaluation of exercise selection and ordering.

**Exercise Parameters**

Training parameters will depend on the exercise modality.

- **Strength:** Number of sets, target repetitions or repetition range, rest time in seconds, and target intensity using RPE (1–10).
- **Cardio:** Duration and cardiovascular intensity.
- **Mobility:** Duration or repetitions, depending on the exercise.

Cardiovascular intensity will initially use three descriptive levels:
- Low.
- Moderate.
- High.

The exercise modality must be explicitly specified so that the output can be validated against the corresponding parameters.

**Load Management**

The LLM will not prescribe mandatory absolute weights in the initial version.

Users will select an appropriate load to reach the target intensity specified in the training plan.

Recording actual loads and adapting future recommendations based on previous sessions will remain potential future developments.

**Exercise Instructions**

Each exercise will include brief, exercise-specific technical instructions.

- Mandatory for every exercise.
- Maximum of two instructions per exercise.
- Relevant to the exercise and adapted to the user's restrictions when applicable.

#### 4. Additional Cardio

Optional section for complementary cardiovascular training when relevant to the user's goals or session requirements.

It may include:
- Activity type.
- Duration.
- Target cardiovascular intensity.
- Additional instructions, when appropriate.

This section is independent of cardiovascular exercises that may already appear in the main training block.

#### 5. Cool-down

Optional section that may include:

- Mobility exercises or stretching.
- Estimated duration.
- Additional instructions.

Its inclusion will depend on the session requirements.

#### 6. General Session Notes

Optional free-text section for complementary information about the training session.

It may include:
- General execution recommendations.
- Effort-related guidance.
- Progression reminders.
- Additional considerations related to the session.

General notes must not replace exercise-specific instructions or compensate for restrictions that should already have been respected during exercise selection.

#### General Considerations

- The output structure must accommodate different exercise modalities and their specific training parameters.
- Not all exercises require the same training fields.
- The estimated session duration must be adapted to the time available to the user.
- The user's usual availability may be used as a reference when no specific duration is provided for the current session.
- The initial user profile and session-specific requests will be defined separately as part of the LLM input structure.
- Persistent identifiers and timestamps must be managed by the backend rather than generated by the LLM.
- Exercise identifiers must be resolved by the backend against an exercise catalogue when available. The LLM must not invent persistent database identifiers.
- Absolute load prescription and longitudinal training adaptation are outside the scope of the initial version.
- The conceptual structure may be refined during implementation if necessary, without changing its fundamental organization.


### P1-02.2 — Define Output JSON Schema

#### Objective
Translate the training plan structure into a validated schema to enforce structural consistency across model outputs and backend systems.

#### Implementation Summary
- **Tooling:** Defined in `src/schemas/training_plan.py` using **Pydantic (v2)** to guarantee structured generation, validate schema compliance, and prevent hallucinated or mismatched workout parameters.
- **Data Models & Separation of Concerns:**
  - `TrainingPlanLLM`: Strictly models the output generated by the LLM (session header, warm-up, main exercise block, optional cardio, cool-down, and general notes).
  - `SystemTrainingPlanOutput`: Enriches `TrainingPlanLLM` with backend-managed identifiers and metadata (`session_id`, `user_id`, `generated_at`, `exercise_ids_resolved`), isolating runtime metadata from LLM prompt completion.
  - `ExerciseItem`: Enforces modality-specific integrity via cross-field validators (`Strength` requires sets, reps, rest, and RPE; `Cardio` requires duration and intensity; `Mobility` requires duration or reps). Constrains technical instructions to a maximum of two cues per exercise.
- **Verification:** Full validation and negative test cases (boundary and modality contamination checks) are documented in `notebooks/schema_validation_demo.ipynb` using `data/evaluation/examples/training_plan_schema_validation.json`.


## P1-03 — Define LLM interaction and Generation

Define how users interact with the AI Fitness Trainer, how their structured profile and free-text request are provided to the LLM, and which instructions guide the generation of a structured training plan.

### P1-03.1 — Define Chat Interaction and User Guidance

#### Objective

Define how users interact with the system immediately before generating a training plan, using a free-text chat input supported by brief guidance examples.

#### 1. Chat Interaction

The interaction will consist of three main elements:

- **Welcome message:** A short message inviting the user to describe the training session they would like to perform.
- **Chat input:** A free-text field where users can describe their training needs naturally.
- **Guidance examples:** A set of optional suggestions displayed below the chat input to help users provide useful information.

No mandatory fields or predefined questionnaire will be required.

#### 2. Welcome Message

The system will display the following introductory message:

"Let's prepare your workout! Tell me what you would like to work on today, and we'll adapt the session to your needs."

#### 3. User Guidance

The system will provide optional examples of information users may include in their messages:

- **Training goal or focus:** Muscle groups, full-body training, strength, hypertrophy, etc.
- **Available time:** Expected workout duration.
- **Preferences:** Preferred exercises, training styles or equipment.
- **Restrictions:** Exercises or movements the user wants to avoid.
- **Current condition:** Energy level, perceived fatigue or desired training intensity.

These suggestions are intended to guide users, not to impose a fixed input structure.

#### 4. Expected Behaviour

- Users can submit requests using natural language.
- All guidance examples are optional.
- The system will combine the user's message with their existing profile information.
- Missing information will be handled using reasonable defaults and available profile data.
- The system may ask for clarification when the request is too ambiguous or essential information is missing.
- Session-specific requests will not automatically modify the user's permanent profile.
- The visual presentation and layout of these elements will be defined during frontend development.

### P1-03.2 — Define LLM Input Structure and Priority Rules

#### Implementation Summary
- **Data Payload (`SessionGenerationInput`):** Combines the filtered `UserProfile`, the natural language `session_request`, and an optional `conversation_context` field for multi-turn chat tracking.
- **Field Filtering & Optimization:** Internal system identifiers (`user_id`) and empty optional fields are excluded via serialization to optimize token consumption and minimize prompt noise.
- **Conflict Resolution & Priority Rules:**
  1. **Safety First (Physical Limitations):** Health restrictions declared in the user profile take absolute priority. If a natural language request conflicts with an active limitation, the system mandates respect for the physical restriction.
  2. **Session Specificity:** The free-text session request dictates the immediate focus of the workout (e.g., specific muscle focus or duration adjustments), provided it remains within the user's experience level and safety boundaries.
- **Verification:** Input payload validation is governed by Pydantic V2 to ensure strict runtime enforcement before model invocation.

### P1-03.3 — Define Base LLM Prompt Specification

#### Objective
Define the foundational system prompt structure for the LLM, establishing core responsibilities, generation guidelines, priority rules, and output constraints, while keeping it adaptable for future model iterations and RAG-based scientific grounding.

#### Prompt Architecture & Design
The base prompt is structured into four core modular steps:
1. **Role and Responsibilities:** Establishes the persona of a professional personal trainer, defines operational boundaries (general fitness vs. clinical/medical exclusion), and mandates strict adherence to system instructions over conflicting user inputs.
2. **Training Plan Generation Instructions:** Outlines core programming principles—personalization, logical exercise selection, appropriate parameters (sets, reps, RPE, rest), time management, and session coherence.
3. **Behavior and Priority Rules:** Implements a strict hierarchical resolution order to resolve conflicts safely:
   - 1. System instructions and safety constraints.
   - 2. User's physical limitations.
   - 3. Specific session request.
   - 4. User profile background.
   - 5. Conversation context.
   - 6. Reasonable defaults.
   - Also dictates ambiguity handling to prevent hallucinations and request clarification when essential data is missing.
4. **Output Requirements:** Enforces structural compliance against the `TrainingPlanLLM` schema, explicitly prohibiting the generation of backend-managed metadata (such as session IDs or timestamps).

#### Future Alignment (Phase 2 & Model Optimization)
- **Extensibility:** The prompt design is intentionally modular to allow seamless integration of retrieved scientific evidence and exercise guidelines via **RAG (Retrieval-Augmented Generation)** in Phase 2.
- **Model Agnosticism:** While drafted for robust general instruction-following, the prompt remains flexible for adaptation once the final production model (and its specific architectural token/structured output constraints) is selected.
